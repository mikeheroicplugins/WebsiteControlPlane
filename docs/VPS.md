# geekheros.com VPS deployment

The control plane now has an independent, same-origin Node.js deployment. It does not require Docker Desktop, a logged-in desktop, the hosted Sites preview, or `npm run dev`. The existing development and Sites builds remain supported. Standard Docker Engine is still used for site isolation; this change removes the Desktop dependency, not the underlying engine.

## Topology and access

Caddy owns public ports 80/443 and terminates HTTPS. Its administrator username/password prompt protects the entire dashboard and API. Passwords are bcrypt-hashed, not stored as plaintext. The gateway listens only on `127.0.0.1:3080`, verifies a separate proxy secret, checks browser origins on writes, and forwards requests to the loopback management agent on 8788. Never publish either management port or a Docker socket/API.

MCP is available at `https://YOUR_MANAGEMENT_HOST/mcp` with its own bearer token, not the browser password. Settings generates the right connection JSON in VPS mode. All 58 tools, including `get_runtime_diagnostics`, are available remotely. A shared MCP token is full administrative authority, including command execution and billable domain operations: give it only to trusted agents. Per-agent telemetry is informational, not strong per-agent identity; use a VPN/firewall for an internal deployment. Browser HTTP Basic sessions are cached by the browser; close the browser/private window to end a session. There is no built-in MFA or multi-user authorization.

## 1. Prepare a fresh Linux VPS

Use a supported Linux distribution with Node.js 22.13+ (Node 24 LTS is suitable), Git, Caddy 2.8+, and Docker Engine. Install the engine using its [official Ubuntu instructions](https://docs.docker.com/engine/install/ubuntu/), not Desktop. Install Caddy using its [official package instructions](https://caddyserver.com/docs/install). Use a dedicated service user:

```sh
sudo useradd --system --create-home --home-dir /var/lib/geekheros --shell /usr/sbin/nologin geekheros
sudo usermod -aG docker geekheros
sudo install -d -o geekheros -g geekheros -m 0700 /var/lib/geekheros
sudo install -d -o geekheros -g geekheros /opt/geekheros/control-plane
sudo install -d -m 0700 /etc/geekheros
sudo -u geekheros git clone https://github.com/mikeheroicplugins/WebsiteControlPlane.git /opt/geekheros/control-plane
cd /opt/geekheros/control-plane
sudo -u geekheros npm ci
sudo -u geekheros npm run build:vps
```

Engine access is effectively host-root authority; only trusted administrators should have control-plane access. Permit SSH from trusted addresses and 80/443 as required; deny public access to 3080, 8788, 8080, 8443 and automatically assigned preview ports. Published engine ports can bypass ordinary UFW rules—verify rules at the provider firewall as well. Site preview ports and the routing gateway are bound to loopback in VPS mode.

For screenshot capture, install a sandbox-capable Chromium/Chrome package on the server. If it is not in a standard location, set `GEEKHEROS_BROWSER_PATH` to its absolute executable path. Run the service as the dedicated non-root user; do not disable the browser sandbox. Confirm your chosen browser package supports headless use under systemd.

## 2. Configure secrets and addresses

Copy `deploy/control-plane.env.example` to `/etc/geekheros/control-plane.env`, owned by root with mode `0600`. Edit it using `sudoedit`:

- Set **two different** random values generated independently by `openssl rand -hex 32` for `GEEKHEROS_AGENT_TOKEN` and `GEEKHEROS_WEB_TOKEN`.
- Replace `control.example.com` in both management settings with your real management domain; point its DNS to the VPS. The public URL must be an HTTPS origin, without a path.
- Set `GEEKHEROS_ADMIN_USER` and paste the hash generated by interactive `caddy hash-password` into `GEEKHEROS_ADMIN_PASSWORD_HASH`. Do not put a plaintext password in this file. See [Caddy authentication](https://caddyserver.com/docs/caddyfile/directives/basic_auth).
- Keep persistent state at `/var/lib/geekheros`, outside the source checkout. This directory contains provider credentials, OAuth tokens, the MCP secret, source checkouts, blueprints, screenshots and backups. Never commit it.

The supplied Caddy template uses ports 3080 and 8080; if you change the corresponding environment ports, update Caddy too. The service file assumes Node is installed at `/usr/bin/node`; adjust `ExecStart` if your installation differs. Do not source the environment file in a shell: it uses systemd environment-file syntax and includes a literal password hash.

## 3. Install the services

```sh
sudo install -m 0644 deploy/geekheros.service /etc/systemd/system/geekheros.service
sudo install -d /etc/systemd/system/caddy.service.d
sudo install -m 0644 deploy/caddy-geekheros.conf /etc/systemd/system/caddy.service.d/geekheros.conf
```

Merge `deploy/Caddyfile` into your existing Caddy configuration; do not overwrite other websites. On a fresh Caddy installation it can be used as the main configuration. Validate with the configured environment using a transient systemd service:

```sh
sudo systemd-run --wait --pipe --collect -p EnvironmentFile=/etc/geekheros/control-plane.env /usr/bin/caddy validate --config /etc/caddy/Caddyfile
sudo systemctl daemon-reload
sudo systemctl enable --now geekheros
sudo systemctl restart caddy
sudo systemctl status geekheros caddy
```

Visit your HTTPS management address and sign in. Settings shows VPS mode, node identity, free storage and the public MCP URL. The service starts after reboot and restarts if either child process fails. Caddy handles certificates for configured domains. Do not put a CDN/proxy in front without reviewing its request timeouts, body-size limits and trusted client-IP chain.

## 4. Configure site routing

For each production **and staging** domain, point DNS to this node and add an explicit Caddy block using the example at the bottom of `deploy/Caddyfile`. Validate and reload Caddy, then launch the matching site in the dashboard. Managed sites use HTTPS URLs in VPS mode. The internal site router is loopback-only on 8080/8443, leaving public 80/443 available to Caddy. WordPress receives a configured HTTPS signal behind the reverse proxy.

The domain provider page manages registrar/DNS settings; it does **not** automatically add Caddy blocks or grant public access. Staging has separate files/database, search-index blocking and outbound-email suppression, but no automatic visitor password wall. Add Caddy authentication or a VPN restriction to staging when its content is private. HTTPS, DNS propagation and internet reachability must be checked on the actual VPS.

## 5. Migrate deliberately

Do not copy a Windows state file into a running Linux service and expect its absolute paths or storage volumes to work. This change does not move sites or modify the existing workstation's data.

1. Create and download current site backups and take an encrypted copy of the full `.geekheros` directory. Record production domains and blueprint/plugin requirements.
2. Stop management writes during a migration window. Provision the target VPS as above and launch a clean target for each site.
3. Import the site's database and files through an established WordPress migration process or a reviewed restoration procedure. Existing dashboard backup IDs refer to archives on their original node; cross-node archive import is not automated.
4. Reconfigure provider credentials, Lovable OAuth and trusted MCP clients on the new node. Move reusable blueprint packages explicitly; do not copy Windows source/archive paths blindly.
5. Test admin login, staging sync, backup/restore, cron, media, mail, screenshots and MCP before cutting DNS over. Retain the old node and an offline backup until validation is complete.

An existing router created with different public port bindings is not silently replaced in VPS mode. Resolve that migration explicitly after backing up its configuration.

## Operations and recovery

```sh
sudo journalctl -u geekheros -n 100 --no-pager
sudo systemctl restart geekheros
```

For updates: preserve `/var/lib/geekheros`, record the previous Git revision, stop the service, pull a reviewed release, run `npm ci` and `npm run build:vps` as the service user, and restart. Keep the prior build/release for rollback. Do not run two agent processes against the same data directory or update while a restore, migration, deployment or purchase is in flight. A process crash during a mutation needs an audit-log and state check before retrying; requests are intentionally not replayed by the gateway.

Back up `/var/lib/geekheros`, the protected environment file and site database/files independently, encrypted and **off the VPS**. Local scheduled backups alone do not protect against host loss. Monitor disk capacity and copy/remove backups according to your retention policy; automatic pruning and off-server replication are not included. Limit public management access by VPN/provider firewall where practical.

## Verification before production use

- `npm run test:runtime`, `npm run build:vps` and `npm run build` pass.
- Direct gateway/agent requests without secrets fail; dashboard access without administrator credentials fails at Caddy.
- Remote MCP without its bearer token fails. An authenticated client discovers 58 tools and can call `get_runtime_diagnostics` and `get_system_info`.
- Settings reports the correct HTTPS URL and persistent storage. No remote UI links point to the visitor's `127.0.0.1`.
- Test an actual site launch, staging round-trip and backup restoration on the target VPS. Reboot it and verify recovery.

Repository checks and isolated gateway tests do not substitute for these host-level acceptance checks.
